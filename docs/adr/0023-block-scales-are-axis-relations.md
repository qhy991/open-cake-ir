# ADR 0023: block scales are axis relations

Status: accepted, 2026-08-25; implemented by Compiler v17.

## Outcome and non-goals

A scale buffer states which FP8 buffer it scales, the granularity along every data axis,
and the concrete order in which those grouped axes appear in scale storage. An MMA
contract that consumes block scales reads two data operands followed by their two related
scale operands. The verifier derives every legal scale extent and refuses a relation the
selected backend cannot implement before lowering.

This change does not add a quantization mode, layout algebra, padded or packed scale
storage, a dynamic extent, grouped/ragged work acquisition, a quantizer operation,
sub-rate TMA pipelines, FP4/UE8M0, or a KDA-version profile. Those mechanisms have
different effects and evidence boundaries. In particular, this slice cannot make a
complete KDA version expressible.

## Evidence and constraints

The KDA v1 MoE authority uses FP8 E4M3 data with FP32 block scales:

- hidden activation `[M, K]` is paired with scale storage `[K/128, M]`;
- a weight `[N, K]` is paired with `[N/128, K/128]`;
- its Blackwell grouped GEMM uses scale granularity `(M=1, N=128, K=128)` and applies
  one A scale and one B scale to each 128-wide partial contraction before accumulation.

Those shapes are not independent buffers. If `K`, the block granularity, or the physical
axis order changes, the scale shape follows. The retained DeepGEMM survey independently
finds the same missing relation, plus padded/packed and dynamic variants that remain out
of this slice.

The paper's P2/P4/P7 boundary requires the scale mechanism to stay visible, statically
checked and updated together with analysis. Treating scales as two extra untyped MMA
reads would let a backend silently choose their association and broadcast.

## Minimal primitives and SSOT

One optional `Buffer.scale_of` relation owns three facts:

```json
{
  "buffer": "a",
  "granularity": [1, 128],
  "axis_order": [1, 0]
}
```

- `buffer` is the FP8 data buffer this FP32 scale buffer describes;
- `granularity[i]` is the number of data elements represented along data axis `i`;
- `axis_order` is a permutation of every data axis and is the order of grouped extents
  in the physical scale buffer.

For data shape `D`, the verifier derives grouped extent
`G[i] = ceil(D[i] / granularity[i])` and requires the scale shape to equal
`[G[i] for i in axis_order]`. Nothing restates the resulting shape in an operation.

The first consuming contract is `triton.dot.fp8e4m3_block_scale_fp32`. Its canonical MMA
read order is data A, data B, scale(A), scale(B). The scale buffers themselves name their
owners, so the verifier can prove the order instead of relying on names. The contract
means FP8 E4M3 inputs, FP32 scales, FP32 accumulation and an explicit sum of independently
scaled K-block contractions.

The owners are:

- typed IR: relation spelling and structural closedness;
- verifier: derived shape/dtype rules, load propagation and MMA association;
- Target: whether the implementation contract is admitted;
- Triton emitter: the exact supported static lowering;
- external oracle and B200 observation: numerical correctness.

## Dataflow and supported lowering domain

The positive Schedule loads data and scales into register tiles. A scale relation must
survive that load: if global `sfa` scales global `a`, staged `sfa_tile` scales the staged
destination of `a`. Changing only one side is a data-consistency failure.

The initial Triton lowering supports the exact KDA-style static subset:

- A relation granularity `[1, block_k]`, stored `[K-block, M]`;
- B relation granularity `[N, block_k]`, stored `[N-block, K-block]`;
- one B-scale group across the emitted N tile;
- exactly two equal, exactly divisible K blocks for A and B.

It statically splits both FP8 tiles into two K blocks, emits one `tl.dot` per block,
multiplies each partial by the corresponding FP32 A/B scales, and accumulates in FP32. A relation outside
that domain remains structurally analyzable but receives a blocking
`MMA_BLOCK_SCALE_UNLOWERABLE` Finding. It never falls back to unscaled `tl.dot`.

## Failure and compatibility semantics

- unknown `scale_of.buffer`, non-FP8 data, non-FP32 scales, wrong rank/permutation or a
  derived-shape mismatch are localized data-consistency Findings;
- scale metadata lost or changed across a load is a data-consistency Finding;
- missing, extra, reversed or unrelated scale reads on the block-scaled MMA are a
  data-consistency Finding;
- an admitted relation outside the emitter's declared static domain is a hardware-
  conformance Finding and cannot reach emission;
- ordinary two-input MMA contracts keep their existing meaning and generated bytes.

Historical Schedules remain valid because `scale_of` is optional. A scale relation has
no compatibility fallback: readers neither infer it from a buffer name nor reconstruct it
from a convenient shape.

## Smallest complete vertical slice and acceptance evidence

The standalone profile is one dense `[M,N,K] = [16,128,256]` contraction with two
128-wide K blocks, FP32 scale storage `[2,16]` for A and `[1,2]` for B, and FP32 output.
It deliberately exercises both non-identity axis order and more than one scale block.

Acceptance requires:

1. the authoring schema and typed parser agree on the relation;
2. relation-shape, dtype, propagation, association and supported-domain failures are
   independently triggerable;
3. the positive and a relation-drift sibling match reviewed Corpus expectations;
4. ordinary emitted profiles retain their lowering digests;
5. the generated kernel compiles and launches on brokered B200 and matches an independent
   dequantize-then-matmul oracle at the preregistered `1e-5` maximum absolute tolerance;
6. complete KDA-version coverage remains 0/57 until grouped/ragged routing, scatter and
   program composition are represented and evaluated together.

The released v17 Corpus Gate matched all 24 cases. The scale-association sibling is
blocking while the positive lowers deterministically. A brokered B200 observation of the
released source compiled, launched and matched all 2,048 outputs with maximum absolute
deviation `1.7881393432617188e-07` against the independent dequantize-then-matmul oracle,
below the preregistered `1e-5` tolerance. No timing was taken and no performance claim is
authorized.
