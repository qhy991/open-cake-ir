\section*{摘要}
\begin{notebox}
高性能实现需要目标特化；一次优化中形成的数据流改写、适用条件与反例，则可能帮助后续
任务减少重复搜索。open-cake-ir 以 Compiler 为核心，用带类型的 Schedule 和 Program
记录执行选择，将经过审查的发现整理为显式变换、目标诊断或编译能力。Agent 在目标侧
重新选择分块、工作分配和资源配置；独立评测确认设备正确性与性能。原生工程探索也可
提供新发现，相关能力在后继提交与新任务中重新验证。

本报告分别讨论表示与诊断、额外材料与变换权限、lowering 自由度和系统演进的作用。
原生 DSL 加等效工具、同动作集合的非 LLM 搜索及来源知识对照，是后续研究的不同入口。
实现基础和局部收益不能直接替代跨目标搜索成本的因果证据。

历史实现章节保留源码 \code{677eb444} 的八个目标、179 项语料预期及各自设备案例；
TinyGEMM2 的性能差距与 MoE 的有界正确性也维持原结论。2026 年 10 月的研究更新统一
各硬件分支的问题、对照和成本口径，已有 Run 保持原有源码、预算和接受规则。
\end{notebox}

\noindent\textbf{关键词：}GPU 内核；条件化改写；目标适配；智能体；编译器；经验复用

\section{问题、研究对象与论点}

以按行计算的 Softmax 为例，公式确定了每行应得到什么结果，却没有规定一个 GPU 程序
处理多少行、由哪些线程完成归约，也没有规定中间值放在哪里。智能体可以尝试多种安排；
其中有的地址或同步关系不成立，有的虽然算对，却比原实现慢。要继续改进，智能体需要知道
具体是哪项选择出了问题，而不只是收到“编译失败”或一个延迟数字。

本报告研究的是这样一套编写环境：智能体修改明确的执行计划，编译器在生成代码前检查
可判断的关系，设备评测再回答结果是否正确、性能是否改善。当任务反复暴露出表达或分析
缺口时，维护者改进编译器，并在后续任务中检验这项改动。贯穿全文的问题是：
\begin{notebox}
\noindent\textbf{核心问题}\quad
怎样把优化发现变成带条件的可执行机制，让 Agent 在目标硬件上重新实例化，并在
相同语义、参考权限和声明预算下减少搜索成本、保持性能竞争力？
\end{notebox}
CAKE 论文提出了编译器与智能体协同改进内核的研究路线\cite{cake}。open-cake-ir 沿着
这一问题独立实现了程序表示、编译检查和实验流程，并把不同硬件上的观察保留在各自的
任务与测量范围内\cite{papercontract}。

\subsection{背景：公式、执行计划与智能体反馈}
数学公式与设备程序之间隔着一层执行安排。以内核中的行归约为例，行块大小改变了每个
程序实例承担的工作；线程分工影响归约时的通信；中间值的存放方式又影响寄存器与共享
内存压力。编译器可以检查一部分地址、数据流和同步关系，物理资源分配与速度则要到
编译产物和设备上观察。因此，一个候选的反馈需要指出检查到了哪一层，以及问题落在哪个
操作或资源上。

这些观察还决定改动应当留在哪个位置。某种分块在当前形状上更快，可以先保留为任务候选；
换到另一目标时，需要重新选参数并验证；若同类改写在不同任务中反复有效，才有理由提炼
带适用条件的编译器变换。报告将依次展示这三层工作所依据的程序、诊断和设备记录。

\subsection{变化中的工具链与编译能力}
固定 GPU 目标并不固定软件编译环境。NVIDIA 的 CUDA Toolkit 12.1 与 12.2 分别列出
不同的 \code{nvcc} 组件版本，发布说明也记录了编译器诊断与 PTX 接口的变化
\cite{cuda121,cuda122}。因此，算子候选的编译和评测需要连同工具链版本一起固定；
硬件目标名本身不足以标识一次实现条件。

智能体可以连续提出新的分块、存储与同步选择。多个任务若反复遇到同一类表达、合法性或
后端生成缺口，修正单个候选无法消除共同的编译器限制。研究者或维护 Agent 依据留存的
计划、诊断和设备观察确定责任层，再把修复、反例及相应分析一同送过语料门与审查。后继
任务在新编译器版本上验收这项能力。

\subsection{CAKE 论文提供的研究起点}
CAKE 让智能体编写一份带类型的硬件执行计划。计划写明资源、线程角色、数据访问和同步；
屏障地址与流水线阶段位等机械细节由编译器推导。编译器先检查程序安全、硬件约束、数据
一致性和调度语义，再把有希望的候选送去编译与设备评测。任务中反复出现的失败，可以
推动后续增加原语、改进检查规则或校准性能估计。CAKE 的重点因此不只是生成更快的内核，
也是让编译环境随着任务一起改进\cite{cake}。

论文在 B200 上用固定形状的 Flash-KMeans 任务比较了两种编写环境：一组由智能体编写
Cake IR，另一组直接编写 CUDA/PTX；目标的低层实现都不向作者开放。两组各运行三次，
共同使用 80M provider-token 截点。这个实验比较的是整套编写环境，包括表示、检查和
反馈，并未单独测量 IR 语法的作用。论文中的 KDA 服务及其他性能数字也属于原研究的结果；
本文讨论本仓库时，会另列其独立运行的证据。CAKE 论文覆盖的目标是 NVIDIA Ampere 至
Blackwell，非 NVIDIA 平台的实现和测量需要另建证据\cite{cake,papercontract}。

\subsection{本工作的定位与证据范围}
Compiler 拥有完整 Program、叶子 Schedule、合法性检查、确定性改写与 lowering；Lab
负责材料、作者与研究处理。工作围绕可复用机制及目标适配组织，具体问题与分支分工见
第\ref{sec:shared-theme}节。原 CAKE 的 IR、诊断和协同演进设计是明确承继的基础。

历史实现章节提供程序表示、检查流程和有界设备案例。研究增量则需要单独检验：带条件
改写是否减少关联修改错误，来源信息是否帮助目标重选，以及这些收益能否覆盖发现、
工具实现与维护成本。新增设计不将工程 Run 重标为受控消融，也不把接受更多候选等同于
更强的正确性保证。

\section{共同研究主题与跨平台实验}\label{sec:shared-theme}

\subsection{从优化发现到条件化机制}
本项目以 Compiler 为核心，研究优化发现怎样成为后续任务可用的机制。一次发现同时包含
可复用的数据流改写和依赖目标的决策：例如分块可以限制活动数据与资源压力，但 tile、执行组
和流水线需要结合目标重新选择。机制保留前后程序、语义条件、目标实现条件、可调决策、
反例和版本范围；收益假设仍由实机确认。\researchrepo{docs/RESEARCH_AGENDA.md}{共同研究约定}
统一各硬件分支的问题与对照，具体实验仍由 Workload、Run 和 Study 的现有职责承接。

研究区分三项假设：表示与工具是否改善有限预算搜索；来源经验和可执行化是否各有增量；
经审查的系统后继是否帮助未参与修复的任务。多目标接入、单次本机加速与一个可调用 pass
分别提供局部证据，不能直接替代这些受控比较。

\subsection{相关路线与增量贡献}
CAKE 和 TIRx Harness 已研究 Agent 编写接口、编译分析与优化反馈\cite{cake,tirxharness}；
Exo 2 与 MLIR Transform 提供可组合、可扩展的调度或编译变换\cite{exo2,mlirtransform}。
AutoTVM 与 MetaSchedule 研究调优、知识迁移和可扩展搜索空间\cite{autotvm,metaschedule}。
AKG kernel Agent 分离优化 sketch 与具体 DSL 生成\cite{akgagent}；KernelBlaster 与 AccelOpt
把经验形成和后续利用作为研究对象\cite{kernelblaster,accelopt}。本项目将这些能力明确作为基础
和对照，贡献需要落到具体机制、目标适配方法及可重复的效果上。

AI lowering 增加了一条重要比较路线：从既有 Triton 程序和固定执行合同生成 PTX，
让模型承担更多底层实现决策\cite{ailowering}。该论文的原 Volta 限定候选与数值验收候选有
不同的最佳结果，提示验证覆盖可能限制搜索；最佳候选表不构成相应程序集合的理论性能上界。
原 Volta 的模型内保证与后续扩展的保证需要分别解释\cite{volta,ailowering}。符号检查、
有限设备测试、计时质量和实际加速也各有自己的验收范围。

共同能力子集用于隔离因素，完整合理能力用于评估覆盖与强实现差距。给定优化源码与只给

差异不自动证明等效。原生接口或表达形式也不决定理论上更高的性能，研究重点是有限预算内
实际找到并独立确认的结果。

\subsection{独立原生发现与后继晋升}
IR 保持默认开发接口。具体假设暴露表达或 lowering 缺口时，Lab 可以在已经准入的路线
启动独立原生工程 Run，保留同一 Workload、精确 Target、oracle 和测量要求，并声明预算、
继承材料和参考访问。冻结 Run 内不切换路线，也不向原研究回填原生成绩。

发现按责任层处理：何时使用和如何选参进入 Lab；可复用改写进入 Compiler pass；兑现
缺口进入 lowering；可建模的非法行为进入 Verifier；真实表达缺口才共同扩展 primitive、
类型、效应和分析。审查与验证完成后，后继提交接受新任务检验。\code{No promotion}
是有效结论。新 Schedule 或 pass 必须重新验证，不能继承来源低层实现的正确性或速度。
人工提炼、自动提炼与使用工具是不同过程，分别记录发现、实现、审查和维护成本。

\subsection{各硬件分支回答同一主问题}
各分支选择自身已能可靠评测的任务，贡献不同技术差异的证据。NVIDIA 优先提供结构性发现、
强原生对照和显式存储/同步案例；MetaX 检验联动分块、产物资源与测量边界；Hygon 检验
目标侧重选、数值行为及寄存器和 scratch；AMD 验证各精确目标的执行宽度、资源与工具链差异；
Metal 检验 threadgroup 分工、存储及表达/评测覆盖。任何平台都可成为来源或目标，
main 维护共享语义和研究口径，不替平台宣布设备资格。

新实验在已有计划和 Run/Study 输入中说明假设、机制与任务、对照、参考权限、预算、
测量合同和停止/确认规则。新优化 Run 默认显式绑定三小时总预算，确认资源包含其中；
专项准入探针另设有界预算。研究若使用不同预算，在执行前对各组一致声明；既有 Run
不追改。这是实验设计约定，不增加一种 Study 或执行器。

发现、目标适配与测试分开。参与过机制或参数选择的任务属于开发证据。未见形状、未见
算子族和新目标分别报告；重复 Run 和计时样本不充当新增任务。按卡位和时间分块，保留
失败与未达到终点的结果。墙钟、token、CPU 准备、编译、排队和设备用量分别记账。
强种子通过验收后，再检验完整 Program、模型或服务的收益。

\subsection{编译器：检查程序，再生成目标源码}
编译器读入完整程序及其各阶段计划，在一个精确目标上检查类型、张量绑定、数据依赖和
硬件约束。检查结果把两个问题分开回答：\code{Assessment.accepted} 说明计划是否符合
通用语义规则；\code{lowering\_eligible} 说明所选后端能否把它生成源码。比如，计划
本身可以表达一种操作，某个后端却尚未实现对应指令，此时反馈会指出后端能力缺口。

通过检查的计划由后端确定性生成可阅读的源码。编译器中的显式改写也必须给出完整的新
候选，或说明为何拒绝改写。这些判断只依赖程序、目标与编译器版本；实验组别和设备测量
由后面的模块处理\cite{architecture,irguide}。

\subsection{实验系统：固定一次优化的条件}
一次运行开始前，实验系统先核对任务、编译器、执行环境、基线和预算，再向编写内核候选的
智能体提供获准查看的任务材料。搜索中，智能体提交候选，控制器记录剩余的编译与评测次数。
搜索结束时，系统从已有候选中固定一个提名，用独立的新样本确认其正确性与性能；确认结果
出现后，提名不再改换。

普通工程运行只需自己的运行规格。研究比较则由研究计划提前分配处理组，并让各组沿用
同一执行与评测流程。旧实验使用的 CampaignLock 保留为输入适配层，历史数据仍按产生
它的版本解释。这使智能体能看什么、能调用什么工具、何时停止，都在结果出现前确定。

\subsection{评测与证据：先判对，再解释速度}
评测模块先用任务合同生成输入，与外部参考逐项核对输出。候选算对之后，才按目标设备的
计时与状态重置约定采集样本，并在需要时运行性能剖析。搜索读数、独立确认和剖析结果
各有单独收据。若计时波动超过质量门，记录说明的是测量尚不足以判定快慢；候选的数值
正确性仍按先前的检查结果保留。

证据模块保存候选文件、事件顺序、评测收据和终态。独立审计可以在不再调用智能体服务或
GPU 的情况下重建运行过程；研究分析只使用通过审计的结果。对多阶段程序，评测还要
核对每次启动的顺序与最终输出，并按实际程序区间计时。单内核的计时收据只能回答那次
内核调用的问题\cite{acceptance}。

\subsection{两个时钟：候选搜索与编译器演进}
候选和编译器沿两条时间线变化。在一次运行里，任务、目标、编译器及测量规则保持固定；
智能体改变的是执行计划。检查与设备评测指出下一份候选该改哪里，也让不同候选的结果
可以在同一条件下比较。

如果多次运行都遇到相同的表达或检查缺口，维护者才在运行之外修改编译器。新版本先经过
语料测试与代码审查，再用于下一轮任务。这样，旧运行的结果仍对应旧编译器，新运行才
能检验编译器改动有没有解决原来的问题\cite{architecture,acceptance}。
这一外环的迭代速度可以按缺口被定位到后继能力通过验收所需的时间衡量，同时记录修复在
未见任务上的复用和回归情况；当前仓库尚无与人工维护流程匹配的迭代耗时对照。

\subsection{显式的计划，而非新的布局代数}
对每一行做 Softmax，任务规定的是结果：若 $m=\max_k x_k$，则
$y_j=\exp(x_j-m)/\sum_k\exp(x_k-m)$。执行计划要补上公式没有写出的事：每个程序实例
处理几行，哪些执行组负责归约，中间结果放在哪里，以及按什么坐标写回。图
\ref{fig:softmax-schedule} 以仓库示例中的 64 行块展示这些选择。

Schedule 把操作、缓冲区、执行组、访问坐标、循环和同步关系存成带类型的结构。
编译器因此可以检查：读取和写回是否指向同一行，两组是否争写同一输出，目标是否接纳
所需指令。它要求作者写明具体的存储与访问承诺，却没有另设一套通用布局代数；Triton
等下游工具链继续负责物理布局、寄存器分配和最终指令选择\cite{irguide,architecture}。

当计算需要多个内核时，Program 将各阶段接成一个完整程序，声明它们共享的输入输出、
执行顺序和张量绑定。此时验收对象是程序的最终输出与完整调用区间，而非某一个阶段的
单独速度。

\subsection{受限 Python 前端与同一规范 IR}
示例把 Python 前端导入为 \code{cake}，用它声明 \code{@cake.schedule} 和张量参数；
函数的第一个形参 \code{lm} 是 Schedule 上下文的语法名字：前端识别它的方法调用，
不会执行一个运行时的 \code{lm} 对象。仓库没有为 \code{lm} 规定缩写含义；把形参
及函数体中的引用一起改名为 \code{ctx}，仍会得到同一份规范 Schedule。\code{lm.program}
选择行块，\code{lm.role} 指定
执行组，角色作用域内的调用描述读取、归约、广播和写回。前端解析受支持的 Python
语法树，并为诊断保留源码位置；它不会运行源文件的导入语句或函数体\cite{irguide}。
下面摘录的是
\repo{examples/python/softmax.py}{当前 Softmax 示例}中的实际操作：

\Needspace{16\baselineskip}
\begin{lstlisting}[style=reportcode,language=Python]
compute = lm.role(execution_groups=[0, 1, 2, 3])
row_block = lm.program(x, axis=0, dimension=1, tile=64)
batch = lm.program(x, axis=1, dimension=0, tile=1)
with compute:
    x_tile = lm.load(x[batch, row_block, :], reuse="reused", id="load_x")
    rowmax = lm.reduce(x_tile, op="max", axis=1, scope="cta", id="row_max")
    shifted = lm.sub(x_tile, lm.broadcast(rowmax, axis=0), id="shift")
    weights = lm.exp(shifted, id="exponentiate")
    rowsum = lm.reduce(weights, op="sum", axis=1, scope="cta", id="row_sum")
    y_tile = lm.div(weights, lm.broadcast(rowsum, axis=0), id="normalize")
    lm.store(y[batch, row_block, :], y_tile, id="store_y")
\end{lstlisting}

示例输入输出都是 $[8,512,128]$ 的 FP32 张量，目标是 \code{sm\_100a}，生成路线为
Triton。\code{tile=64} 使每个实例负责 64 行；四个执行组完成同一份行块上的工作。
行最大值和行和先广播回列维度，再参与逐元素计算；最后仍按原来的行块坐标写回。
换一种分块或分工，编译器会重新检查计划，设备评测再判断它是否算对、是否更快。

作者在 Python 装饰器中无需手填任务内容的哈希。独立调用编译器时，可以直接检查计划；
进入实验系统后，系统先核对目标、生成路线和公开张量接口，再绑定这次运行冻结的任务。
这样，任务身份由实验输入决定，作者只编辑实现方案。具体准入规则见
\repo{docs/PYTHON_FRONTEND.md}{前端合同}。

\subsection{从 Python Schedule 到 Triton：一次实际生成}
对上面的 Softmax，固定源码 \code{677eb444} 的 Compiler 先把 Python 语法树转换为
带类型的 Schedule，再检查形状、访问、操作依赖和目标约束。本例的结构检查通过，
Triton 生成路线可用；报告另给出 \code{REGISTER\_PRESSURE} 与
\code{RESIDENCY\_BOUND} 两条提示。随后执行 \code{lower}，得到下面的 Triton
内核体节选；两处较长的地址表达式只按页宽重新折行。代码中的 \code{CAKE\_OP}
注释保留了原计划的操作 ID，便于从生成代码
找回 \code{load\_x}、\code{row\_max} 等编写位置。

\noindent\textbf{对照速览：}\code{lm.program} 的 64 行块变成程序 ID 与行偏移；
\code{lm.load} 的访问变成地址、边界掩码和 \code{tl.load}；行归约与广播变成
\code{tl.max}/\code{tl.sum} 和 \code{[:, None]}。编译器还把四个执行组写入
启动参数 \code{num\_warps=4}。

\Needspace{28\baselineskip}
\begin{lstlisting}[style=reportcode,language=Python]
row_block = tl.program_id(0)
batch = tl.program_id(1)
row_block_offsets = row_block * BLOCK_ROW_BLOCK + tl.arange(0, BLOCK_ROW_BLOCK)
x_d2_offsets = tl.arange(0, D_X_2)
y_d2_offsets = tl.arange(0, D_Y_2)

# CAKE_OP:load_x
load_x_ptrs = (
    x + batch * N_ROW_BLOCK * D_X_2
    + row_block_offsets[:, None] * D_X_2
    + x_d2_offsets[None, :]
)
x_tile = tl.load(
    load_x_ptrs,
    mask=row_block_offsets[:, None] < N_ROW_BLOCK,
    other=0.0,
    eviction_policy="evict_last",
)
# CAKE_OP:row_max
rowmax = tl.max(x_tile.to(tl.float32), axis=1)
# CAKE_OP:shift
shifted = x_tile - rowmax[:, None]

# CAKE_OP:exponentiate
weights = tl.exp(shifted)

# CAKE_OP:row_sum
rowsum = tl.sum(weights.to(tl.float32), axis=1)
# CAKE_OP:normalize
y_tile = weights / rowsum[:, None]

# CAKE_OP:store_y
tl.store(
    y + batch * D_Y_1 * D_Y_2
      + row_block_offsets[:, None] * D_Y_2
      + y_d2_offsets[None, :],
    y_tile,
    mask=row_block_offsets[:, None] < D_Y_1,
)
\end{lstlisting}

摘录省略了函数签名和宿主启动包装。完整文件还核对输入的形状、dtype、设备和连续性，
随后将 $512/64=8$ 个行块与 8 个 batch 组成 \code{(8, 8, 1)} 网格，传入
\code{BLOCK\_ROW\_BLOCK=64}、\code{num\_warps=4} 和 \code{maxnreg=96}。
其中的 \code{tl} 是实际导入的 \code{triton.language}；前面的 \code{lm} 只是
Cake 前端识别的形参名。

读者可在固定源码的根目录运行下列命令，查看包含函数签名、输入检查和启动包装的完整
生成文件。这个步骤只生成 Python/Triton 源码，设备编译、正确性和速度另由评测确认。
\begin{lstlisting}[style=reportcode]

\subsection{精确目标文档}
同一份执行计划语言要面对不同硬件，具体能力由目标文档（Target）说明。当前八个目标
分属 NVIDIA、Apple、AMD、Hygon 和 MetaX；每份文档分别声明线程组宽度、存储空间、
可用指令、代码对象与资源限制。编译器按目标的精确 ID 准入，缺少的硬件事实报告为
“未建模”。Triton、Metal、原生 CUDA 与 CuTe DSL 则是生成源码的路线；其中 Triton
服务多个厂商，不以厂商名划分公共 IR\cite{targets,architecture}。

\subsection{表示变更的验收义务}
新原语会改变作者能写什么，也会改变编译器必须检查什么。因此，一项 IR 扩展要同时
说明结果类型、读写效果、合法性规则、分析所需信息和目标上的实际行为，再用正反用例
检查这些关系。对于能够由现有原语组合的算子，先建立任务合同和参考实现；遇到确实
无法表达的执行行为，再扩展语言与后端\cite{cake,irguide}。

\section{编译器：从局部化检查到目标源码}

\subsection{分层拒绝与反馈}
编译器先把作者的程序构造成带类型的 IR，再检查程序中的关系是否成立。例如 FMA
需要三个输入；若候选漏掉第三个读取，检查结果会在 \code{operations[3].reads}
指出 \code{ELEMENTWISE\_ARITY}。作者据此补上缺失的数据边，而不必先编译、运行 GPU
再从错误输出猜原因。其余检查归入四类：
\begin{notebox}
\noindent\begin{tabularx}{\linewidth}{@{}Y Y@{}}
\code{schedule\_semantics} 调度语义 & \code{hardware\_conformance} 硬件符合性 \\
\code{data\_consistency} 数据一致性 & \code{program\_safety} 程序安全
\end{tabularx}
\end{notebox}
一条诊断（Finding）带有稳定代码、位置、类别及阻断范围，Python 前端还能把位置指回
源文件。建议性提示另存，不改变候选的检查结论。通用规则通过后，后端还会检查这条
生成路线能否支持候选所用的操作与硬件特性。通过这些门，意味着候选可以进入下一步
编译；设备上的答案与速度仍要分别测量\cite{architecture,acceptance}。

\subsection{源码生成与下游工具链}
检查通过后，后端生成一份可阅读的目标源码。选择 Triton 时，这份源码还要交给对应厂商
的 Triton 工具链；Metal、原生 CUDA 和 CuTe DSL 各有自己的生成与编译入口。目标文档
声明最终代码对象的类别，执行器按该类别加载产物。这样，从执行计划到 GPU 结果的过程
可以逐段追踪：源码是否生成、工具链是否编译、设备是否可加载、输出是否算对、计时是否
可信，各有自己的记录\cite{architecture}。

\section{实验方法与证据等级}

\subsection{一次 Run 的四阶段}
一次运行从固定任务开始，沿四个阶段推进：
\begin{enumerate}
\item 作者提出结构不同的执行计划或完整程序，记录每次改了什么；
\item 编译器先检查类型、合法性和后端支持，再用有目标校准的成本估计安排设备评测顺序；
\item 对可运行候选核对完整输出；正确后按目标设备的协议计时，并在需要时采集剖析数据；
\item 根据具体诊断继续修改候选，或将反复出现的编译器缺口留给后继版本处理。
\end{enumerate}
成本估计节省搜索时的设备时间，最终接受仍取决于外部答案和实机测量。每种目标硬件
分别声明计时器、测量区间与样本前的设备状态；缺少这些条件时，报告保留计时覆盖缺口。

\subsection{双时间尺度与 Finding 的负责位置}
图\ref{fig:two-clocks}展示了两种改动的节奏。一次运行只改变候选程序，任务、编译器、
目标和测量规则保持原样。运行留下的错误、正确性收据与性能样本，为下一轮候选提供
依据。运行结束后，维护者再查看反例：问题是候选写法、检查规则、生成路线，还是缺少
一种表达？需要修改编译器时，改动先成为新提交，通过语料门和审查，再进入下一次运行。
有些性能差距只适合继续探索候选，记录“暂不提炼通用变换”也是结论。

\subsection{研究对照的单位和参考访问}
研究比较以一次独立运行为单位，而不是把同一运行中的多个候选当作重复样本。干净起点
允许作者看任务规格、外部答案和高层代码，目标的完整低层实现则留在作者视野之外；
研究已知内核的复现时，参考实现可以成为允许的材料。比较 Cake 和直接 CUDA 编写环境，
还须固定模型、任务、预算与评测规则。搜索读数用于挑选候选，结论取自候选固定后的
独立确认。基础设施中断在报告中记为缺失，保留它已经消耗的成本\cite{papercontract,study}。

\subsection{证据保存、回放与结论资格}
每份候选、评测收据和终态都按事件顺序追加保存。审计者可以离线重算候选选择与停止
状态，并检查报告是否来自这些原始材料。还要分别核对归档内容能否完整回放，以及当时
的写入与发布过程是否满足文件监管要求。前者说明记录可读，后者决定它能否用于晋升或
研究估计。协议将两项分别记为 \code{archive\_integrity} 与
\code{filesystem\_custody\_verified}。历史运行始终按当时的源码与协议审计
\cite{acceptance}。

\subsection{NVIDIA：任务族覆盖与外部比较}

为每个固定形状保留原起点、改写产物和外部实现。截至 2026-09-21，26 个任务中有

领先、6 项未检出达到预设门槛的差异、4 项合格落后、4 项缺少合格的外部计时；其余

逐任务记录更能说明优化发生了什么。任务 022 的四组候选对外部实现取得合格领先，

中间候选改善，面对外部实现仍落后。这些结果把“相对自己的上一版进步”和“达到外部
实现水平”分成两件事。独立 NCU 剖析可帮助解释工作分配与资源使用；计时判断仍依据
原来的 CUPTI 样本及质量门\cite{nvidia}。

B300 的服务实验、CTA 宽度验证、FlashInfer 改写和 CAKE 任务复现使用不同基线与
协议，分别放在报告中。B200 的 FMA、状态操作和 QSA 案例也沿用各自的历史提交。

\subsection{Apple、Hygon、AMD：不同结论等级}

\subsection{MetaX：单内核、完整输出和实际 Run 分别验收}

\subsection{案例 C：B300 MoE 的事件流水与 native CUDA lowering}\label{sec:weave-case}
\begin{notebox}
\noindent\textbf{2026-09-28 后续案例 \quad B300-M4 \quad 最多四卡}\par
\noindent\small 固定的四 rank BF16 MoE 层中，N128 候选在四路由 $\times$
$K=4/2/1$ 的 12 个控制上有 \textbf{0/50,331,648} 个 FP64-oracle 失败、
\textbf{960/960} 个 CPU/GPU tile-event 计数一致；12 个控制均记录到计算任务
与下一事件生产重叠。此处是有界正确性和执行证据，不是对开源实现的加速声明。
\end{notebox}

这一增补的实验代码单独固定于尚未合入主线的 \code{2c638aad}，
作业编号、外部证据根与结论边界见\weaverepo{docs/WEAVE_CASE_STUDY.md}{MoE 案例记录}。
\code{RankedTileEffects.analyze}
由 ProgramMap 推导各阶段的 CTA 工作单元与安全任务容量；
\code{lower\_ranked\_tiles}
把 up/gate、activation、down 的 Cake Schedule 与事件发布、前驱依赖和有界偷取
绑定为一个完整的 B300 worker。一个 rank 的一层只启动一次持久 cooperative grid：
前 $c$ 个 CTA 生产路由、Bin 和 tile，其余 CTA 消费就绪任务；生产者完成事件工作后
可按预算领取剩余任务。时间重叠通过任务完成计数在下一事件生产期间增长来核对，
并非仅依据两段时间窗口相交推断。

优化不是一次性换掉后端，而是按失败证据修改 lowering。最初每事件一次 launch
变成每层一次，样本中的 layer kernel 数由 92 降至 16，却未得到整体延迟收益。
下一事件 lookahead 与双角色流水建立了实际任务重叠，早期完整层计时仍接近持平。
随后把同 GPU 生产者 barrier 的 PTX acquire/release 收窄为 device scope，
跨 GPU 发布仍保留 system scope；远端 BF16 payload 在对齐时使用 128-bit PTX
加载/存储，非对齐子视图走标量路径。\code{emit\_tensor\_tile\_stage}
进一步把 activation 从每 CTA 一行改为四行、六个 warp 各一行，并给最后的不足六行
加掩码；N128 版本同时改变 TMA box、MMA 形状、TMEM 列数、共享内存位置与输出偏移。
这些资源和任务容量随 Schedule 派生，不由 Evaluation 另行指定。

\section{与 CAKE 对照：相同的问题，不同的证据}

\section{跨硬件复用：从一次改写到可检验的收益}

\subsection{可复用的是机制，参数要在目标卡重选}
一次优化既可能发现可复用的做法，也会得到只适合当前设备的参数。比如，融合私有的
中间张量可以省去一次写回和重读；能否融合取决于消费者、生命周期与舍入语义。具体的
tile、执行组和流水线深度，则要在目标卡上重新选择。可确定性表达的改写可以成为带
前提和拒绝原因的显式 pass；只有一次有效的局部参数选择，仍作为任务经验保留
\cite{transfer}。

\subsection{E/P 四组实验}
若要知道经验究竟提供了多少帮助，先要把“让智能体读说明”和“让智能体调用现成改写”
分开。图\ref{fig:ep-study}以 $E$ 控制额外机制材料，以 $P$ 控制显式 pass 的调用权，
形成四种条件。四组共享任务、编译器、目标设备、正确性和计时规则；工具权限由运行环境
实际隔离。$P1$ 组仍需知道调用的最小接口，所以 $E$ 测量的是接口之外的说明和案例。
所引主体快照提供软件协议；本文不由其直接报告四组处理效果\cite{study}。
后继实验须按第\ref{sec:shared-theme}节的共同主题及各自冻结的 Study 解释。

令 $p_{ep}$ 为在预注册预算内经新鲜确认、达到本机预定改善阈值的 Run 比例。预定主要对比为
\begin{align*}
\Delta_E&=\tfrac12[(p_{10}-p_{00})+(p_{11}-p_{01})],\\
\Delta_P&=\tfrac12[(p_{01}-p_{00})+(p_{11}-p_{10})],\\
\Delta_{EP}&=p_{11}-p_{10}-p_{01}+p_{00}.
\end{align*}
一次独立运行是重复单位。正式研究按任务等权汇总，保留各任务内四组的配对关系；
搜索成本、预算耗尽和基础设施缺失也按事先约定记录。四组全部运行并经共同确认后，
才能计算上面三个处理效果。

\subsection{从 B300 到 Hygon：可执行与性能的分界}
\repo{docs/OPTIMIZATION_TRANSFER.md}{迁移专题}记录了一次具体尝试。B300 上的
\code{pairwise\_sqdist} 候选把 K 维按 256 分块；在固定 FP32 形状上，五类输入检查
和 CUPTI 配对计时通过，相对本机基线从 411.7945 降到 53.856\,$\mu$s。
将同一数学任务准备给 Hygon BW1101 时，团队保留张量、输入、参考答案和容差，先把
旧版 Schedule 的角色表示显式适配到当前 \code{execution\_groups}。适配后的候选及
同卡起点均通过编译器检查，并由 Hygon Triton 编成 HSACO。

原 \code{bw1100} 节点的八卡被其他 GLM 进程占用，实验止于离线准入。另一台
\code{bw1100-1} 具有空闲 BW1101，但宿主内核和环境与前者不同；因此先为该节点
单独捕获 Executor，再在干净源码 \code{4c9f4cc0} 上运行相同合同。五类输入在
计时前后均判对；新鲜 HIP 配对确认质量通过，同卡起点/来源 K=256 候选为
517.9645/748.749\,$\mu$s，十对均是起点更快。故该机制\textbf{能够正确执行，
原参数却在此节点产生负迁移}。本地串行锁不能排除没有使用同一锁的外部任务；
不同 CUPTI/HIP 计时器的绝对时延也不构成跨卡速度比。

在运行下一次设备实验前，冻结两个只改 K tile 的 Hygon 后继：128 和 64。
离线编译均报告零 scratch，分别占 252 和 148 个 VGPR；按预定的资源排序只选择
K=64 上卡。它相对 K=256 的生成源码仅改变分块值与调度身份。在相同五类输入、
whole-K 起点及 HIP 配对协议下，新鲜独立确认全部判对并通过计时质量门，起点/候选
为 518.524/189.586\,$\mu$s（2.735 倍），十对均是候选更快；K=128 没有设备计时。
因此，\emph{K 维分块这一来源机制可以在目标卡重新选参后奏效，但来源参数不可照搬}。
另在上卡前冻结一个未见的同算子形状 \code{R=1024,K=512,N=64}，只比较已选 K=64
与该形状的 canonical whole-K 起点，不再试其他 tile。五类输入在首次及新鲜独立确认
中均零不匹配、计时质量通过；确认中位数为 106.232/97.593\,$\mu$s（1.0885 倍），
十对均为候选更快。第二个形状提供有限的 Hygon 本机形状泛化证据，但收益远小于
K=1024 的 2.735 倍；B300 没有在新形状上的来源性能收据，也没有跨算子结论。
这是一例限定形状的人工机制迁移和 Hygon 本机收益，并非控制作者与预算、随机分配
材料 $E$ 或变换权限 $P$ 后得到的 Agent 处理效果。

难点也并非单一后端开关：同一带循环归约的 Schedule 在当前 Metal 路线无法表达；
Triton 能向 AMD、Hygon 生成代码，却不保证源参数的资源分配或速度；同 ISA 的
第二台 Hygon 宿主仍需独立 Executor；C550 的容器锁边界和 M2 的计时质量分别限制
设备主张。可表达性、目标选参、宿主身份、测量与因果归因须分层验收。

\section{限制、可复查性与结论}

Open-Cake-IR 已经把候选生成、静态检查、目标代码生成和设备反馈接成一条可追踪的路径。
在主体快照源码上，179 项语料符合预期；在若干固定 Workload 上，也已有设备正确性与局部性能
结果。这些结果回答了“系统能否表达、检查并运行具体候选”。要回答“这一机制能否稳定带来
跨任务、跨平台收益”，还需要更完整的目标侧测量和预注册对照实验。

\subsection{解释结果时的四项限制}
\textbf{与 CAKE 的关系。}本文复现的是论文描述的设计问题与实验思路，并独立实现
Compiler。论文公布了系统机制和汇总结果，但缺少把原始编译器、完整 IR 与 Verifier、
agent scaffold、clean-start 轨迹及计时细节一起重建的材料。因此，同名任务的对照
应从输入合同、参考实现和测量范围逐项核对\cite{papercontract}。

\textbf{平台覆盖。}五家厂商、八份 Target 文档界定了可声明的目标；每个平台还须单独
取得工具链、数值、计时器和 profiler 的运行收据。179 项 Corpus Gate 尚未检查
\code{apple\_gpu\_family7} 与 \code{apple\_gpu\_family9}。MetaX 的完整输出验证和
AMD 的计时器调查，也分别处于不同的证据阶段\cite{status,architecture}。

\textbf{性能范围。}一个形状的候选优于本机基线，并不意味着它胜过外部专家实现，或能直接
用于多形状应用。后者还涉及分派守卫、尾部输入、回退路径和框架开销。历史 QSA 数字覆盖
完整 Program 的 GPU 区间；M17 数字覆盖单内核。两者都不能直接换算成模型或服务延迟。

\textbf{机制归因。}工程 Run 和局部消融可以发现问题、改进系统。若要判断作者环境或迁移
材料带来了多少增益，还须固定处理条件，进行独立 Run 和共同确认，并说明缺失结果如何
计入分析。$E/P$ 四组的实机对照尚待开展。

\subsection{下一步的可检验目标}
后续实验按第\ref{sec:shared-theme}节统一问题和证据口径。先确保目标基线、完整输出、
计时和 profiler 可用，再依次检验同动作集合的非 LLM 对照、原生 DSL 加等效工具的表示
对照，以及来源经验与可执行化的增量。缺少合格低层路线时明确报告覆盖，不借其他目标
的资格启动实验。反复出现的缺口通过 Finding、审查和后继提交处理；未参与机制开发的
任务检验复用，完整 Program 和应用收益在强种子上单独验收。

\repo{examples/python/softmax.py}{当前 Softmax 文件}是第 4 节运行示例的完整可读源码：
\begin{lstlisting}[style=reportcode,language=Python]
from open_cake_ir.compiler import frontend as cake

@cake.schedule(name="softmax-b8-smoke", target="sm_100a", backend="triton",
               entry_point="cake_softmax_b8_smoke",
               residency={"ctas_per_multiprocessor": 4,
                          "registers_per_thread": 96})
def softmax(lm, x: cake.Tensor((8, 512, 128), "fp32"),
            y: cake.Tensor((8, 512, 128), "fp32", mode="output")):
    compute = lm.role(execution_groups=[0, 1, 2, 3])
    row_block = lm.program(x, axis=0, dimension=1, tile=64)
    batch = lm.program(x, axis=1, dimension=0, tile=1)
    with compute:
        x_tile = lm.load(x[batch, row_block, :], reuse="reused", id="load_x")
        rowmax = lm.reduce(x_tile, op="max", axis=1, scope="cta", id="row_max")
        shifted = lm.sub(x_tile, lm.broadcast(rowmax, axis=0), id="shift")
        weights = lm.exp(shifted, id="exponentiate")
        rowsum = lm.reduce(weights, op="sum", axis=1, scope="cta", id="row_sum")
        y_tile = lm.div(weights, lm.broadcast(rowsum, axis=0), id="normalize")
        lm.store(y[batch, row_block, :], y_tile, id="store_y")
\end{lstlisting}
这里的 Python 接口通过 AST 构造与 JSON 相同的规范计划；\code{Compiler.load()}
默认读取项目的当前配置。要在具体 GPU 上运行，还需匹配目标工具链，并完成正确性与
性能验收。\repo{docs/PYTHON_FRONTEND.md}{Python 前端文档}列出了支持的语法及源码
位置诊断。
