\section*{摘要}
\begin{notebox}
\noindent\textbf{问题。}智能体能提出 GPU 内核的候选实现，但一次失败或一项延迟读数，
难以说明问题属于调度、表达能力、目标准入还是测量质量。
\par\smallskip
\noindent\textbf{方法。}系统用带类型的执行计划描述单个内核，以完整程序组织阶段。
编译器定位错误；实验系统固定任务和预算；评测检查外部答案、设备计时与性能剖析；
证据系统留存原始观察。重复缺口在运行之外由后继提交修复。
\par\smallskip
\noindent\textbf{证据。}独立实现已声明五家厂商的八个精确目标，当前源码的 179 项语料检查
符合预期。NVIDIA、Apple、Hygon 和 MetaX 各有范围不同的设备结果；AMD 的计时边界仍待
解决。与 CAKE 导出产物重叠的 TinyGEMM2 固定形状已通过严格数值门，但性能差距显著。
跨硬件知识处理的增量收益尚无实机因果估计。
\end{notebox}

\noindent\textbf{关键词：}GPU 内核；中间表示；静态验证；智能体；实验可复查性；跨硬件优化

\noindent{\sffamily\bfseries\color{accent} ABSTRACT}\par\vspace{0.35em}
{\small\raggedright\hyphenpenalty=10000\exhyphenpenalty=10000\noindent
open-cake-ir independently implements a CAKE-inspired system in which agents author typed,
hardware-explicit schedules, receive localized compiler feedback, and validate candidates against

\section{问题、研究对象与论点}

本文的智能体（Agent）负责提出和修订执行计划；GPU 内核是在加速器上并行执行的计算程序；
Compiler 检查计划并生成目标代码。给定同一数学算子，GPU 实现仍须决定任务分块、线程分工、
存储层次、访问坐标、同步与执行顺序。
一个只输出延迟的搜索过程很难说明某次失败属于候选调度、编译器表达能力、硬件准入，还是测量噪声。
CAKE 论文提出让 Agent 编辑显式执行计划，并以编译器分析和外部评测形成反馈闭环\cite{cake}。
open-cake-ir 是对这一研究路线的独立工程实现；论文报告的模型实验和速度数字不作为本仓库结果\cite{papercontract}。

本报告的研究对象是\textbf{可复查的 Agent 编写环境}：一份候选包含什么决策，系统能在什么范围内拒绝，
设备证据如何决定接受，以及真实缺口怎样改变下一版 Compiler。核心问题可以表述为：
\begin{notebox}
\noindent\textbf{核心问题}\quad
在保持 Workload 语义和实验条件可追溯的前提下，怎样让 Agent 的 Kernel 决策可检查、
让失败有负责位置，并让重复经验进入后继编译能力？
\end{notebox}
本文主要陈述三项已实现的机制：\textbf{显式的 Program/Schedule 合同}、\textbf{分层诊断与目标精确准入}、
\textbf{冻结运行和追加式证据}。跨硬件知识迁移的增量价值是后续实验问题，不是现有软件实现的推论。

\subsection{背景：公式、执行计划与智能体反馈}
同一按行归约公式可以采用不同的行块、执行组、存储位置和归约顺序。候选从数学式走向设备
内核时，正确性义务没有消失，反而增加了地址域、同步、资源和目标指令等约束。若编写环境
只给出编译错误、数值通过位和一个延迟，智能体难以区分三种不同的下一步：修复当前候选、
改进生成路线，或补足表示与检查规则。资源分析与 profiler 可以缩小解释空间，但不能自动
证明唯一原因。本文因此沿着\emph{任务语义、执行决策、检查反馈、设备观察}四层组织叙事。

编写 GPU 内核还需要区分两种结果。一个固定形状上更快的内核属于该任务的优化；将同一
机制用于另一形状或硬件，要重新验证目标资源、数值和计时；将其提升为通用编译器规则，
还须说明适用条件、拒绝反例和后继任务中的作用。把这三个层次混在一张加速比表中，会掩盖
系统能力演进本身需要的证据。

\subsection{CAKE 论文提供的研究起点}
CAKE 论文将智能体编写的硬件执行计划、编译前分析与外部评测放在同一个循环中。其 Cake IR
显式记录资源、角色、访问和同步，而把屏障地址、阶段位等机械细节交给 lowering；布局没有
成为作者必须操作的一阶代数。编译器以程序安全、硬件符合性、数据一致性和调度语义的局部
诊断筛选候选，成本模型只在有目标校准时用于设备时间之前的排序。反复出现的真实失败推动
后继 IR、Verifier、lowering 或校准变化；最终正确性和速度仍由外部参考与设备测量决定\cite{cake}。

该论文的代表性因果实验是在 B200 的固定 Flash-KMeans 形状上，以隐藏目标低层实现的起点
比较 Cake IR 编写环境和直接 CUDA/PTX 编写环境。论文报告每组三次独立运行、共同的
80M provider-token 截点，并把结果归于\emph{整套编写环境}，而非孤立的 IR 语法。
其性能、KDA 服务与 dispatcher 结果属于原论文的报告值；本仓库不能把它们作为本地复测
数据。CAKE 的公开论文还说明目标主要是 NVIDIA Ampere 至 Blackwell，非 NVIDIA 后端的
实现与迁移成本没有在该论文中测得\cite{cake,papercontract}。

\subsection{本工作的定位与当前贡献}
open-cake-ir 是沿这一问题重新构造的独立系统。它把 Compiler 做成可单独调用的核心，
使 Workload、研究处理、作者控制和证据监管分别由明确的层负责；Target 以精确文档声明
硬件事实，五个 Vendor 在同一公共表示下各自拥有生成和执行边界。这样的实现提供了检查
不同目标与不同来源证据的公共接口，但\textbf{公共接口不意味着同等设备资格或同等性能}。

本文可支持的当前贡献有三项：一是可编写、可检查、可生成的 Program/Schedule 与精确
Target 合同；二是冻结 Run 内优化与 Run 外编译器演进的分离，以及可回放的候选、诊断、
确认和终态；三是多目标接入和有界设备案例，为后续跨硬件机制检验提供可运行的研究基础。
第三项中的\emph{跨硬件增量收益}仍是待验证问题，不能由路线接通或一个目标的本机优化推出。
第\ref{sec:results}节将每个结果限定到相应的任务、目标、计时和证据级别。

本项目另有三条实现边界。\textbf{第一，目标精确匹配。}目标未声明的事实报告为未建模，
目标不支持的指令或代码对象由其拥有者明确拒绝，不能通过名称相近的架构静默降级。
\textbf{第二，结构合法与设备正确分开。}静态分析可能有漏报或误报，后端会引入未在逻辑
Schedule 中显式分配的物理资源，实际正确性与延迟须由设备观察决定。
\textbf{第三，Compiler 与实验处理分离。}编译器不读取 Study 分组、provider 或证据存储；
一次冻结 Run 的候选只在同一 Compiler 和 Workload 合同内比较，编译器变化在后继提交
及语料验证后进入下一轮\cite{architecture,acceptance}。

\section{系统合同与职责边界}

\subsection{从任务到可审计结论}
任务合同（Workload Contract）固定数学语义、输入域、外部标准答案和容差。执行计划（Schedule）
描述一个内核的资源、执行组、操作、地址与同步；完整程序（Program）再声明公共张量、阶段顺序和绑定。
运行规格（RunSpecification）固定一次优化的源码、目标、材料、工具权限和预算；研究计划（StudyPlan）
仅在研究对照时进一步固定处理、分配、
终点与分析。这些对象的职责不同，不能用一个候选的局部通过来代替 Study 结论\cite{architecture,study}。

\begin{table}[htbp]
\centering\small

Compiler 是独立产品核心，不导入 Lab、provider、Workload 实现或证据库。Lab 调用 Compiler 与

实验策略偷偷进入 Schedule 的语义判断。系统源码与边界见\repo{docs/ARCHITECTURE.md}{架构章节}和
\repo{CONTEXT-MAP.md}{职责地图}。

\subsection{Compiler：独立解释完整程序}
Compiler 读取一份完整 Program 及其叶子 Schedule，在同一精确 Target 与同一源码提交上
解释类型、绑定、依赖和硬件承诺。\code{Assessment.accepted} 表示结构与通用规则的结论，
\code{lowering\_eligible} 则记录后端能否兑现；两者分开允许可表达但未实现的路线给出
明确资格拒绝。显式改写返回完整后继候选或局部拒绝，不让 Lab 持有第二套图语义。只有
通过门的计划才由后端确定性生成可检查源码。Compiler 不知道研究组别、provider、设备
分配、oracle 或最终 Claim\cite{architecture,irguide}。

\subsection{Lab 与研究分配：冻结作者能看什么、能花多少}
独立工程 Run 的输入是一份 \code{RunSpecification}；若研究需要比较条件，\code{StudyPlan}
事先分配相同 Run 引擎的处理组、估计量与缺失规则。Lab 在触发作者、工具链和 GPU 之前
核对 Workload、Compiler/Executor、provider、基线和预算。作者提交结构化候选，Ralph
控制搜索、编译和确认额度；搜索停止后固定提名，再用新鲜 Evaluation 收据确认，不因确认
失败临时换候选。历史 CampaignLock 只在输入边界转换到共同 Run，而不构成另一套执行
循环。这样，一次实验的处理从准备到终态均有单一负责位置。

\subsection{Evaluation 与 Evidence：判断和留存分开}
Evaluation 接受封存的可运行候选，按 Workload 材料化输入，以外部 oracle 判对；正确性
通过之后，才按精确目标的计时、状态重置与 profiler 协议收集样本。搜索、独立确认和
profiler 各有自己的收据；CV 质量失败属于测量观察，不把数值正确候选改记为算错。
Evidence 保存候选字节、事件顺序与终态，离线审计在不调用 provider、GPU 或网络的
条件下重建协议、资格和缺失。Study 使用通过审计的 Run，而不是用作者自述或某个搜索
最低读数生成估计。完整 Program 的每个阶段保留编译和 launch 身份，最终输出及程序
区间单独验收；单次 dispatch 的计时器不自动具备多阶段 Program 资格\cite{acceptance}。

\subsection{两个时钟：候选搜索与编译器演进}
内循环在\textbf{冻结的} Compiler、Workload、Target、oracle 和测量合同下进行：生成结构不同的候选，
先通过构造检查、Verifier 和后端预检筛选，再对幸存者做设备正确性、计时与剖析，最后把诊断
送回下一次候选。外循环由累积的 Finding 触发：若问题属于通用合法性、缺失原语、lowering 或
目标校准，维护者在后继提交中修改其负责模块，验证后才开启新 Campaign。一次运行不能边测边
改变尺子\cite{architecture,acceptance}。

\section{程序表示：任务、完整程序与执行计划}

\subsection{显式的计划，而非新的布局代数}
受限 Python 前端与 JSON 文档形式进入同一规范的 typed Schedule；Python 入口解析受支持的语法，
并不执行任意宿主 Python 程序。Schedule 记录执行组、缓冲区、访问映射、循环、操作与同步，
性能相关的硬件选择因此可被检查。它没有把 layout 建成一阶代数；对目标硬件的具体存储与访问
承诺由相应 Target 和后端解释并验证。Triton 路线仍把部分物理 placement、寄存器分配与指令
选择交给下游工具链，不能把其生成结果当作 Schedule 已经精确指定的事实\cite{irguide,architecture}。

例如对一行 Softmax，Workload 给出 $y_j=\exp(x_j-m)/\sum_k\exp(x_k-m)$，其中
$m=\max_k x_k$；候选 Schedule 另选每个执行组处理的行、列块、归约方式与写回坐标。
若读取、归约和写回对同一行的坐标约定不一致，问题属于数据一致性；若两个执行组写同一输出，
问题属于程序安全；若目标不提供所需指令，则属于硬件符合性或后端资格。数学式相同不能消除
这些执行计划差异。

Program 负责多个 Schedule 的公共输入输出、阶段顺序与张量绑定。完整 Program 的正确性要检查
所有阶段的最终输出；单 Kernel 的计时或剖析不能自然推广为 Program、模型或服务收益。

Python 导入或函数体；JSON 仍是同一规范 Schedule 的序列化形式。正常导入一个受信任的示例
与把不受信任的候选交给 AST 入口，是不同的安全边界\cite{irguide}。如下摘录自
\repo{examples/python/softmax.py}{当前 Softmax 示例}：

作者不必在 Python 装饰器中手填 Workload 内容身份。独立使用 Compiler 时可直接检查
源码；进入 Lab Run 时，Lab 先核对精确目标、生成路线和公开 tensor ABI，再由已冻结

\begin{lstlisting}[style=reportcode,language=Python]
compute = lm.role(execution_groups=[0, 1, 2, 3])
row_block = lm.program(x, axis=0, dimension=1, tile=64)
batch = lm.program(x, axis=1, dimension=0, tile=1)
with compute:
    x_tile = lm.load(x[batch, row_block, :], reuse="reused", id="load_x")
    rowmax = lm.reduce(x_tile, op="max", axis=1, scope="cta", id="row_max")
    shifted = lm.sub(x_tile, lm.broadcast(rowmax, axis=0), id="shift")
    weights = lm.exp(shifted, id="exponentiate")
    rowsum = lm.reduce(weights, op="sum", axis=1, scope="cta", id="row_sum")
    y_tile = lm.div(weights, lm.broadcast(rowsum, axis=0), id="normalize")
    lm.store(y[batch, row_block, :], y_tile, id="store_y")
\end{lstlisting}

原示例的完整签名固定输入输出为 $[8,512,128]$ FP32，并指定 \code{sm\_100a} 与 Triton
生成路线；这里仅省略装饰器和函数签名以突出工作划分与数据流。\code{tile=64} 是每实例
处理的行数，四个执行组是调度承诺；它们并不从 Softmax 公式自动得出。行最大值和行和必须
显式广播到列维后才能与输入 tile 对齐，写回仍使用相同行坐标。调整这些选择后，Compiler
重新检查，设备评测再决定正确性和收益。

\subsection{完整 Program 的阶段与绑定}
一个 Program 声明公共张量、各阶段顺序以及输入输出绑定，叶子阶段包含完整 Schedule。
例如选择性注意力程序需要池化、评分、Top-$k$、索引展开和注意力阶段，并在循环中保存
选择与归约状态；单 Kernel 合格不能替代阶段间张量一致性与最终输出的检查。程序级变换
可以改变阶段数量，所以比较前须固定 Workload 与终点，再以完整 Program 的调用路径判对
与计时。第\ref{sec:results}节把历史 QSA 程序作为这一范围的案例，而不把它当成通用 Program
自动优化已经完成的证据。

\subsection{精确目标文档}
当前源码声明八个精确目标，分属 NVIDIA、Apple、AMD、Hygon 和 MetaX 五个 Vendor。
精确目标文档（Target）拥有自己的线程组宽度、存储空间、指令合同、代码对象及资源事实；
未声明的事实报告为“未建模”，不借用相似目标的常数。后端是生成机制，不是厂商身份：
现有 Triton、Metal、原生 CUDA 与 CuTe DSL 四条路线，各自声明可生成的代码对象。
编译器对目标和后端做精确匹配，不能把未声明目标降级到邻近架构\cite{targets,architecture}。

\subsection{表示变更的验收义务}
新增 IR 原语须同时给出类型、效应、合法性、静态分析和目标行为；只有语法而没有这些语义，
不能成为已准入能力。仓库将易编写、性能决策可见、规范形式、构造时类型检查、可分析、
语料门、分析一致与硬件根据作为表示的八项设计约束\cite{cake,irguide}。某算子若能由现有原语
组合实现，应先添加 Workload Contract；只有真实表达缺口才要求扩大 Compiler。

\section{编译器：从局部化检查到目标源码}

\subsection{分层拒绝与反馈}
Compiler 首先解析与构造类型正确的 IR，然后按四类合同检查：
\begin{notebox}
\noindent\begin{tabularx}{\linewidth}{@{}Y Y@{}}
\code{schedule\_semantics} 调度语义 & \code{hardware\_conformance} 硬件符合性 \\
\code{data\_consistency} 数据一致性 & \code{program\_safety} 程序安全
\end{tabularx}
\end{notebox}
Assessment 中的 Finding 指向字段或源码区域，带稳定代码、类别、严重度和阻断范围；
非阻断的 guidance 与拒绝原因分开。后端预检负责该生成路线特有的能力边界。静态分析只能
在已建模的范围内阻断；未声明的资源上限和下游产生的物理资源需求需要另行观察\cite{architecture,acceptance}。

一个可复查的小反例是 FMA 候选漏掉第三个输入：构造仍指向同一数学操作，Assessment 在
\code{operations[3].reads} 报 \code{ELEMENTWISE\_ARITY}，指出该操作需要三个输入。
作者因此可以修复具体数据边，无需先耗费设备时间。通过静态检查只允许候选继续；
它不证明工具链编译、GPU 数值正确或速度收益\cite{architecture}。

\subsection{源码生成与下游工具链}
合法 Schedule 经选定后端输出可检查的目标源码。Triton 路线再通过厂商对应的 Triton 工具链
编译；Metal、原生 CUDA 与 CuTe DSL 路线各保留自己的预检与生成条件。Target 声明的代码对象
随生成路线进入工具链和 Executor，不能由目标名字猜测架构。生成源码、编译产物、设备可加载性、
外部正确性与实测延迟是五个递进但互不等同的检查点\cite{architecture}。

\subsection{从 Finding 到物理资源观察}
Assessment 把阻断性 Finding、仅报告的覆盖限制及非阻断 guidance 分开。它能告诉作者
哪个字段违反了哪类合同，也能在缺少目标校准时拒绝给出伪精确的成本顺序。逻辑 Schedule
中的寄存器 tile 不等于编译后每线程寄存器数；后端可能引入暂存、栈或共享内存。工具链
产物的资源报告可以在不启动 GPU 的条件下收集，实机 profiler 才能观察目标运行时瓶颈。
两类观察以候选和源码身份关联，但不互相替代。详见

\section{实验方法与证据等级}

\subsection{一次 Run 的四阶段}
系统按下列顺序运行候选搜索：
\begin{enumerate}
\item 生成结构不同的 Schedule 或 Program 候选，并记录具体变更；
\item 以 IR 构造、Verifier、backend preflight 和有目标覆盖的成本估计筛选，未覆盖时明确弃权；
\item 对幸存者使用外部 oracle 检查完整输出，再在目标计时器、状态重置与质量门下测量，并保留 profiler 观察；
\item 将失败归于候选、Verifier、成本模型、IR 或 lowering，决定继续搜索或登记后继 Finding。
\end{enumerate}
成本估计用于设备时间之前的排序与过滤，不能决定最终接受。每个目标分别声明计时器、测量区间
和样本前设备状态；缺少其中一项时应报告测量覆盖限制，而不是继承其他目标的延迟语义。

\subsection{双时间尺度与 Finding 的负责位置}
图\ref{fig:two-clocks}把两类变化隔开。在内循环，一个 Run 固定 Workload、Compiler、
目标、作者可见材料和测量合同；作者可修改候选，外部系统追加诊断、正确性和计时收据。
在外循环，维护者根据保留的反例判断应改变候选、Verifier、IR、lowering、目标事实或
成本模型。若要改 Compiler，改动在新提交及语料验证后才供下一次 Run 使用；原 Run 的
解释不随源码后来移动。一次性能差距也可能得出 \code{No promotion}，不自动铸造成 pass。

\subsection{研究对照的单位和参考访问}
正式比较的实验单位是独立 Run，不是 Turn、候选或检查点。干净起点只能看到规格、oracle、
高层代码和被授权的参考资料，不能读取目标的完整低层实现；已知 Kernel 复现则可以读取该实现。
直接低层编写与 Cake 编写是 Authoring Environment 的不同处理条件，需要共同的目标、任务、
模型、预算与评测协议。搜索内的最佳读数须经候选固定后的独立确认；基础设施故障应保留为缺失，
不能重写成数值错误\cite{papercontract,study}。

\subsection{证据保存、回放与结论资格}
候选、评测和终态以追加方式保存，报告由原始事件、产物和收据派生。一次 CPU 或离线回放
可以重新计算选择和终点状态，但不能替代当时的设备样本。\code{archive\_integrity}
验证归档内容是否能按协议回放，\code{filesystem\_custody\_verified}验证写入和发布环境的
监管前提；两者相互独立。若后一条件缺失，即便 Git 检出内容可读，也不能把它提升为
资格、估计或性能晋升。历史证据在其原提交和原协议下解释，不由本报告的较新编译器重新
赋予资格\cite{acceptance}。

\subsection{历史 B200 案例的放置方式}
\href{https://github.com/qhy991/open-cake-ir/releases/tag/research-preview-2026-09-06}{2026 年 9 月旧版报告}
给出两个值得保留的有界案例。QSA 在固定 $T=32768$ 的完整 Program 上，历史确认

\section{跨硬件知识迁移：机制与待验证估计量}

\subsection{可复用的单位与负责位置}
候选优化可能包含两种不同的知识：一个带适用条件的\textbf{语义改写}，以及在某个硬件上选出的
tile、执行组或 pipeline 参数。前者可在 IR 中形成显式 pass，声明前提并返回完整候选或拒绝原因；
后者要在目标 Target 上重新选择和验证。以私有中间张量的融合为例，数据流私有性、舍入、消费者
和生命周期是机制条件；寄存器占用与具体收益属于目标设备事实。来源设备的速度比不随机制迁移
\cite{transfer}。当一次研究没有可推广改写时，记录 \code{No promotion} 是正常结果。

\subsection{E/P 四组实验}
仓库已实现对经验材料 $E$ 与显式变换调用权 $P$ 的四格隔离和软件协议，但尚没有共同目标、
基线与预算下的实机迁移收益实验。四组分别为 $E0P0$、$E1P0$、$E0P1$ 和 $E1P1$；
$P1$ 的最小接口合同本身会暴露必要机制信息，因而 $E$ 的效果只指额外说明与案例。
各组共享 typed IR、Target、oracle、计时质量门和可表达的基础能力。材料与调用权限须通过
真实隔离执行，不能只由提示词声称关闭\cite{study}。

\subsection{已到达工具链的离线迁移实例}
当前\repo{docs/OPTIMIZATION_TRANSFER.md}{迁移专题}新增了一条 B300 到 Hygon BW1101
的有来源路径。源任务 \code{pairwise\_sqdist} 在 B300 固定 FP32 形状上，候选把 K 维
按 256 分块，来源 Run 的五类输入前后检查和 CUPTI 配对质量通过，相对本机固定基线
411.7945/53.856\,$\mu$s（7.646 倍）。移向 \code{gfx938} 时，Workload 的数学、
张量、五类输入、oracle 与容差保持一致；历史 Schedule v1 不能直接改目标，先显式适配
到 v2 \code{execution\_groups}。适配后，固定 Compiler 接受并 lower 候选与同卡 starter，
Hygon Triton 3.6.0 将两者编成 HSACO，并通过 CPU 配对准入。

这条路径已经证明\emph{带有一次明确 IR 版本适配的机制能够到达目标工具链}，但尚未在
Hygon 加载、对完整输出判对或计时。B300 的 7.646 倍没有转移为 Hygon 的性能成绩，
也不是 $E/P$ 四格对照的因果结果。目标设备阶段需要五类 case、同卡基线配对、声明计时
边界和独立确认，再决定是否把这一机制记作有效迁移。

\section{限制、可复查性与结论}

本文的最强软件结论是当前源码上的表示、检查、生成和控制协议，以及 179 项语料预期相符。
最强设备结论是指定源码、目标与固定 Workload 上的正确性和局部合格改善。当前材料不足以
估计跨硬件经验迁移的因果收益、普遍性能优势，或模型与服务层面的端到端收益。
静态分析的覆盖也受目标声明和后端实际资源分配限制；缺乏目标计时校准时应报告未知，
而不是给出没有根据的延迟预测。

后续工作以同一职责边界推进：补齐各平台完整 Program 与目标框架验收；在有原始证据的
目标上校准测量与成本估计；将重复的失败形成有反例的 Verifier 规则、IR 能力或 guarded pass；
最后用预注册 E/P 实验检验迁移增量。这个顺序让 Kernel 结果、Compiler 演进与研究归因各有
自己的证据和版本。

\subsection{解释结果时的四项限制}
\textbf{实现来源。}CAKE 论文公开了系统机制与聚合结果，但原始编译器版本、完整 IR/Verifier、
agent scaffold、原始 clean-start 轨迹和部分计时细节并未作为可逐字节重建的同一包公开。
本仓库的 Compiler 是独立实现，不能把相似接口或同名任务说成原实现的逐字节复现
\cite{papercontract}。

\textbf{平台不均。}五个 Vendor、八个 Target 文档说明目标集合与离线准入；每个目标的
工具链、数值合同、计时器和 profiler 资格仍由自己的收据决定。\code{apple\_gpu\_family7}
和 \code{apple\_gpu\_family9} 在当前 179 项 Corpus Gate 中没有被检查；其他目标的
通过数不能补上这种缺席。MetaX 的完整输出 case 与 AMD 的计时器调查也不能占用彼此的
结论等级\cite{status,architecture}。

\textbf{局部性能与应用。}单形状候选可能在自己的基线前改善，同时仍落后于外部专家实现。
多形状 dispatcher 的守卫、fallback、尾部和框架开销还需要独立验证。本文的 QSA
历史案例只计完整 Program 的 GPU 区间，不能外推为模型或服务延迟；M17 的单内核
提升也不自动成为多阶段 Program 提升。

\textbf{研究归因。}普通工程 Run、provider 资格、软件消融夹具及有条件的性能观察都能
帮助完善系统，但只有预注册处理、独立 Run、共同确认和完整缺失规则才能估计作者环境
或机制材料的因果效应。当前 $E/P$ 四组尚无这种实机结果。

\subsection{下一步的可检验目标}
后续工作首先补齐目标侧完整输出、计时区间、状态重置与测量分辨能力，再扩展同一任务的
Program 和框架接入。在固定来源平台机制与目标开发集后，冻结 $E/P$ 四组的材料、工具
权限与任务清单；各目标只相对自己的本机基线报告确认率、搜索成本和条件性能。对实际反复
出现的表达或分析缺口，保留触发 Finding、反例、后继提交及其验证，再观察新能力是否帮助
后续任务。这样才能逐步回答“协同演进产生了什么可复用能力”，而不靠跨平台拼接的加速比。

\repo{examples/python/softmax.py}{当前 Softmax 文件}是第 4 节运行示例的完整可读源码：
\begin{lstlisting}[style=reportcode,language=Python]
from open_cake_ir.compiler import frontend as cake

@cake.schedule(name="softmax-b8-smoke", target="sm_100a", backend="triton",
               entry_point="cake_softmax_b8_smoke",
               residency={"ctas_per_multiprocessor": 4,
                          "registers_per_thread": 96})
def softmax(lm, x: cake.Tensor((8, 512, 128), "fp32"),
            y: cake.Tensor((8, 512, 128), "fp32", mode="output")):
    compute = lm.role(execution_groups=[0, 1, 2, 3])
    row_block = lm.program(x, axis=0, dimension=1, tile=64)
    batch = lm.program(x, axis=1, dimension=0, tile=1)
    with compute:
        x_tile = lm.load(x[batch, row_block, :], reuse="reused", id="load_x")
        rowmax = lm.reduce(x_tile, op="max", axis=1, scope="cta", id="row_max")
        shifted = lm.sub(x_tile, lm.broadcast(rowmax, axis=0), id="shift")
        weights = lm.exp(shifted, id="exponentiate")
        rowsum = lm.reduce(weights, op="sum", axis=1, scope="cta", id="row_sum")
        y_tile = lm.div(weights, lm.broadcast(rowsum, axis=0), id="normalize")
        lm.store(y[batch, row_block, :], y_tile, id="store_y")
\end{lstlisting}
这里的编写接口以 Python AST 构造与 JSON 相同的规范计划；\code{Compiler.load()}
默认读取项目的当前配置。复制这个示例不会自动取得某台 GPU 的可运行产物或性能资格。
现有\repo{docs/PYTHON_FRONTEND.md}{Python 前端文档}列出允许的语法及源码位置诊断。
