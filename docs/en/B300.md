# Open-Cake on B300

[中文](../B300.md)

B300 has a separate `sm_103a` Target (compute capability 10.3). B200 keeps
`sm_100a`. This first slice supports Python Schedule authoring and Triton for
three existing operators. CuTe, checked CUDA assets, historical direct-CUDA
studies and portfolio remain outside this B300 slice.

| Python starting point | Workload | Cases |
| --- | --- | --- |
| [RMSNorm](../../examples/python/b300_rmsnorm.py) | [FP32 RMSNorm v2](../../contracts/workloads/rmsnorm-fp32-v2.json) | 6 |
| [GEMM+bias](../../examples/python/b300_gemm_bias.py) | [BF16/FP32 GEMM+bias v2](../../contracts/workloads/gemm-bias-bf16-fp32-v2.json) | 5 |
| [Indexed gather](../../examples/python/b300_indexed_gather.py) | [BF16 gather v2](../../contracts/workloads/indexed-gather-bf16-v2.json) | 4 |

These Python sources emit the same kernel body and compile/launch requirements
as their JSON baselines; provenance comments may differ. Gather indices share
one zipped domain, use rank-one INT32 registers and must have equal lengths.
The frontend retains their explicit read/dependency edges and infers `[J,D]`,
with no negative-index wrapping or changed masking. Buffer-index syntax is
currently load-only.

```python
from open_cake_ir.compiler import Compiler

compiler = Compiler.load(".", "compiler/revision.lock.json")
assessment = compiler.assess_file("examples/python/b300_rmsnorm.py")
lowering = compiler.lower(assessment)
print(lowering.target)  # sm_103a
```

[Baseline preparation](../../examples/paired_triton/prepare.py) still specializes
all cases using the selected v2 Workload, exporting JSON and Triton outside the
checkout. The [B300 Study template](../../contracts/studies/matched-search-triton-b300-optimization-template.json)
accepts `python_source`; its pending provider binding still requires live qualification.

To qualify both IR and native Triton authoring environments, use
`tools/qualify_codex_provider.py`, specify
`--maximum-candidates-per-turn`, and select
`contracts/providers/codex-triton-optimization-output-schema-v1.json`.
This schema corresponds to `--feature-policy closed_research`.
The remaining arguments bind the actual provider, model, workspace and external
evidence directory. This checks initial and resumed submissions in two separate
threads and archives the JSON candidates. It does not compile or execute them,
or establish kernel correctness or performance. The selected output schema owns the arm
pair; there is no separate `--comparison-arm` setting. All qualification uses Ralph.

Workload, Schedule, actual compilation, Candidate, manifest and device must agree
on the exact target. Device checks precede module load; function binary version
must then match that target. The Executor needs a separately verified B300 host
environment, including compiler, CUPTI timing and profiler files. Its historical
`b200-vN` namespace is an opaque software id, not hardware qualification.

B300 inherits no B200 occupancy, peak or cost calibration. Persistent grids are
refused before emission when the Target has no SM count. Static/CPU evidence
does not establish GPU correctness, timing, agent benefit or framework acceptance.
See [ADR 0053](../adr/0053-b300-is-an-exact-target.md) for the design and release gates.

## Paired measurement against one frozen baseline

Stable templates cover [RMSNorm](../../contracts/studies/matched-search-triton-b300-optimization-template.json),
[GEMM+bias](../../contracts/studies/matched-search-triton-b300-gemm-optimization-template.json)
and [gather](../../contracts/studies/matched-search-triton-b300-gather-optimization-template.json).
Each arm has three prescheduled independent runs with 150000 tokens, at most four
turns and three candidates per turn. Every candidate uses the same sealed baseline
in ten alternating AB/BA pairs, five in each order. Each cohort has 25 cold-L2
CUPTI samples and checks all 42 callback outputs. Maximum CV is 0.05; directional
descriptions use a 1.05 ratio and six pair wins. This is a new assay policy, not a
B300 calibration or a requirement to achieve speedup. Correct stable slower and
`close_null` results remain valid observations. Confirmation runs freshly and
profiling remains separate.

Create one external JSON binding document with `schema_version: 1` and the four
absolute file locators `qualification_path`, `qualification_anchor_path`,
`runtime_config_path`, `fixed_baseline_bundle_path`. The last may reference an
existing worker `request.json` and its relative artifact files without rewriting
that historical request. All files stay outside source worktrees. The binding
cannot override provider model, effort, tools, budget or analysis.

After the successor Executor and live provider are qualified, run
`lab preflight <stable-study> --execution-bindings <external-bindings> --output <external-lock>`,
then the existing `lab execute --lock <external-lock> --runtime-config <external-config> --evidence-root <external-evidence>`.
Machine and software bindings belong to the Campaign Lock; the historical freeze
tool must not rewrite the stable Study. The current closed provider explicitly
disables Code Mode and its host while retaining shell restrictions. It requires a
new real two-turn qualification receipt. Neither historical single measurements
nor CPU tests qualify the new GPU assay. See [ADR 0055](../adr/0055-fixed-baseline-paired-execution.md).
