# 在 B300 上使用 Open-Cake

[English](en/B300.md)

B300 使用独立的 `sm_103a` Target，计算能力为 10.3。B200 的 `sm_100a`
仍保留。第一版 B300 支持现有 Python Schedule 和 Triton 路线；CuTe、
checked CUDA assets、历史 direct-CUDA/portfolio 实验尚未扩展到 B300。

| 起点 | Workload | 用例数 |
| --- | --- | --- |
| [Python RMSNorm](../examples/python/b300_rmsnorm.py) | [FP32 RMSNorm v2](../contracts/workloads/rmsnorm-fp32-v2.json) | 6 |
| [Python GEMM+bias](../examples/python/b300_gemm_bias.py) | [BF16/FP32 GEMM+bias v2](../contracts/workloads/gemm-bias-bf16-fp32-v2.json) | 5 |
| [Python indexed gather](../examples/python/b300_indexed_gather.py) | [BF16 gather v2](../contracts/workloads/indexed-gather-bf16-v2.json) | 4 |

Python 起点与对应 JSON 基线生成相同的 kernel 主体及编译/启动参数。
注释中的来源信息可以不同。gather 的两个索引逐项配对，长度必须相同；
负索引不回绕，越界结果为正零。前端把索引寄存器加入 load 的显式读取和依赖，
结果形状为 `[J,D]`。这段索引语法当前只支持 load。

可以先进行静态检查和源码生成：

```python
from open_cake_ir.compiler import Compiler

compiler = Compiler.load(".", "compiler/revision.lock.json")
assessment = compiler.assess_file("examples/python/b300_rmsnorm.py")
lowering = compiler.lower(assessment)
print(lowering.target)  # sm_103a
```

各用例的 JSON/Triton 配对基线仍由
[prepare.py](../examples/paired_triton/prepare.py) 生成。选择对应 v2 Workload，
输出目录放在 checkout 外。Lab 的
[B300 实验模板](../contracts/studies/matched-search-triton-b300-optimization-template.json)
支持 `python_source` 提交，但模板中的 provider 仍待真实资格验证。

验证 IR 与原生 Triton 两个 authoring 环境时，使用
`tools/qualify_codex_provider.py`，同时指定
`--maximum-candidates-per-turn`，并选择
`contracts/providers/codex-triton-optimization-output-schema-v1.json`。
这份 schema 对应 `--feature-policy closed_research`。
其余参数绑定实际 provider、模型、工作目录和外部证据目录。这个检查只验证
两个独立会话各自完成初始提交和续轮，以及 JSON 候选的完整归档；不编译或
运行候选，不证明 kernel 正确性或性能。比较两端由所选输出 schema 决定，
无需另设 `--comparison-arm`。所有资格验证都使用 Ralph 两文件接口。

Workload、Schedule、实际编译结果、Candidate、manifest 和设备必须使用同一
Target。加载模块前检查设备，加载后检查 CUDA 函数的 binary version；B200 与
B300 混用会被拒绝。Python 环境、Triton、CUPTI、计时工具和 profiler 需要新的
B300 主机绑定。Executor 的历史 `b200-vN` 名称只是软件版本命名，不是硬件证明。

当前 B300 Target 不继承 B200 的 occupancy、peak 或成本校准。缺少 SM 数量时，
persistent grid 会在 lowering 前明确拒绝。静态检查、源码等价和 CPU 测试不等于
GPU 正确性、性能、agent 优势或框架端到端验收；这些结论分别需要对应实验证据。

设计和发布边界见 [ADR 0053](adr/0053-b300-is-an-exact-target.md)。

## 固定基线的成对测量

三个稳定模板分别用于 [RMSNorm](../contracts/studies/matched-search-triton-b300-optimization-template.json)、
[GEMM+bias](../contracts/studies/matched-search-triton-b300-gemm-optimization-template.json) 和
[gather](../contracts/studies/matched-search-triton-b300-gather-optimization-template.json)。
每臂预排三次独立 run；每次预算为 150000 tokens、最多四轮、每轮三个候选。
每个候选都与同一份已封存基线测量十对，AB/BA 交替，各五对。
每组有 25 个冷 L2 CUPTI 样本，并检查全部 42 次回调的输出。最大 CV 为 0.05；
方向描述采用 1.05 倍和六次 pair wins。它们是新实验的测量规则，不是 B300
成本校准，也不要求候选必须加速。正确但更慢或 `close_null` 都是有效结果。

新执行绑定保存在 checkout 外的 JSON 文件，格式为：

```json
{
  "schema_version": 1,
  "qualification_path": "/external/provider/receipt.json",
  "qualification_anchor_path": "/external/provider/anchor.json",
  "runtime_config_path": "/external/campaign/runtime.json",
  "fixed_baseline_bundle_path": "/external/baseline/request.json"
}
```

路径指向真实、已封存的外部文件；基线可直接引用规范 worker 的旧 `request.json`
及同目录 artifact。绑定不能替换模型、推理强度、工具权限或研究预算。
先通过新的 Executor 和 provider 资格检查，再使用规范入口：

```sh
open-cake-ir lab preflight contracts/studies/matched-search-triton-b300-optimization-template.json \
  --execution-bindings /external/campaign/bindings.json --output /external/campaign/lock.json
open-cake-ir lab execute --lock /external/campaign/lock.json \
  --runtime-config /external/campaign/runtime.json --evidence-root /external/campaign/evidence
```

具体机器和软件版本只进入 Campaign Lock；不要使用旧 freeze 工具改写稳定 Study。
closed provider 显式启用本机 CLI 所需的 Code Mode host，仍禁用 shell、浏览器、
网页搜索、插件和多 Agent。host 从 CLI 安装目录的规范查找顺序中解析；其路径和
字节身份进入资格证明和 Campaign Lock。每次首次调用或恢复调用前都会重新核对，
helper 缺失、变化或出现优先级更高的替代文件都会拒绝调用。
配置变化需要新的真实双轮 receipt；已有单候选计时和旧 receipt 不能替代它。
新成对执行仍需真实 B300 canary；CPU 测试不能证明 GPU 测量。
见 [ADR 0056](adr/0056-fixed-baseline-paired-execution.md)。

规范 worker 是 `python -m open_cake_ir.tasks.evaluate`。在 broker 的子进程中，
用 `env` 把 `PYTHONPATH` 明确设为本次固定源码的 `src` 目录，并使用 Executor
固定的 Python；不能依赖环境里可能指向旧源码的 editable 安装。
直接执行本次源码的 `src/open_cake_ir/tasks/evaluate.py` 也会加入对应 `src`。
严格的 Workload loader 是 `tasks.workloads.load_workload`，外部基线读取仍由
`lab.bindings.load_baseline_bundle` 负责。旧 `tools/evaluate_flash_candidate.py`
路径已退休，历史请求中的该路径只保留为原运行记录。
