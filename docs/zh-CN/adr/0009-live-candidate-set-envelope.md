# ADR 0009：多个候选装进一个固定提交文件

[设计目录](README.md) · [英文决定与资格记录](../../adr/0009-live-candidate-set-envelope.md)

**原文状态：已接受，2026-08-24。** 后继工作区接口见 [0048](0048-agent-runs-use-task-agents-and-ralph-control.md)。

一轮可以写几个候选，与一轮可以测几个候选，是两个不同预算。`maximum_candidates_per_turn` 是正整数的写作上限；`searches_per_turn` 是独立的 GPU 测量上限，不能据此增加作者上限，也不要求每轮写满。

唯一提交文件是 `candidate-set.json`，包括 `schema_version`、`arm` 和非空 `candidates`。Cake 成员是计划对象，CUDA 成员是 UTF-8 源码字符串。文件使用键排序、紧凑 UTF-8 JSON，末尾恰好一个换行，数组顺序就是候选顺序。

适配器不沿链接读取，先核对环境和数量，再交给已有构建、检查、去重、已发布排序和搜索路径。文件缺失、格式不规范、空集合、超过数量或环境不符，在编译和 GPU 前成为协议故障；某一个成员自身有错，则保留它自己的拒绝记录。缺排序覆盖时保留作者顺序。

旧单候选协议只用于旧实验回放，同一 Run 不能有两种可写提交形式。主要作者是唯一提交者，辅助调查不拥有预算、评测或判断权。

原文验收依次覆盖零 GPU 三候选、真实两轮 provider 传输、小规模真实 GPU 两候选搜索。初次 v1 的目录遍历和 JSON 问题保留为失败；v2 每边写三份、测两份，各有四份收据，共八份，均一次目标调用、零备用调用。它只证明候选集合接通，未产生组间比较或论文结果。
