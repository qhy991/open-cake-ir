# IR 能表达什么：从真实优化工作找需求

[中文目录](README.md) · [英文原始记录](../IR_COVERAGE.md)

本页用中文解释原文的背景、决定和结论范围；逐项长表、精确来源及原始记录由链接中的原文负责。

**历史调查，记录截至 2026-08-28。表里的 YES、部分和 NO 属于当时范围，不是今天的能力表。**

本调查把本机 B200 的 MoE 优化和手写 PTX 阶段作为独立来源，检查“真实工作需要作者明确哪些选择”。论文强调线程角色、屏障、流水线、TMA 和 TMEM；实际优化还反复遇到任务遍历顺序、驻留数量、读取宽度、缓存策略和数据复用。

| 当时检查的 15 类选择 | 当时结论 |
| --- | --- |
| 输入形状决定配置、两配置分发 | 属于 Schedule 上层，不由单 kernel 决定 |
| CTA 遍历、驻留数量、块几何、Split-K、声明资源 | 有相应表达；资源分析仍需区分精确声明和物理分配 |
| 多种流水线深度、读宽与缓存、片上 swizzle、量化缩放、矩阵方向 | 部分表达 |
| 调用者目标所有权、预计算任务表、独立累加器数量 | 当时缺失 |

原文统计 5 类完整、5 类部分、5 类没有；它是这份调查的分类，不能当全项目支持率。特别是寄存器逻辑压力后来被反例推翻了下界解释，真实分配仍靠编译产物。

一个关键约束是：CUDA Graph 回放时，问题大小可能就在 GPU 内存里；让 CPU 先读会引入同步。`valid_extent` 后来只补了固定容量内设备有效前缀，仍不是一般设备任务表或调度器。

原文逐项记录持久网格先于遍历顺序、maxnreg 真正传到后端、缓存组合在 ptxas 被拒绝等观察，说明“有字段”还需要证据证明字段真有效。只在源码里看到一个参数不能算硬件行为通过。

历史补充依次解释独立 top-k、tanh 实现约定、FP8 缩放、有效长度、分组 GEMM、索引 load、加权合并、原子保留和受限索引 store。各自算对不等于完整 KDA；该历史快照仍为完整版本 `0/57`。原子保留的 64 输出有正确性，受限 store 的首次 B200 工作在目录准入前停止，不能混合。

要看后来的决定，读[中文 ADR 目录](adr/README.md)；要判断今天一个具体计划，运行当前固定版本的 assess。完整的 15 轴说明、来源路径与旧观察表保留在原文。
