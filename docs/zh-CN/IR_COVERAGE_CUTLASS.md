# CUTLASS 调查：除了数据大小，还要描述协作规则

[中文目录](README.md) · [英文原始记录](../IR_COVERAGE_CUTLASS.md)

本页用中文解释原文的背景、决定和结论范围；逐项长表、精确来源及原始记录由链接中的原文负责。

**历史调查：2026-08-24，CUTLASS 4.5.2 的 SM100 源码。**

这次查看 36 类调度选择，其中 8 类能直接对应当时 IR，包括 warp 角色、1SM/2SM MMA、流水线深度、操作数方向与来源、遍历顺序和尾部子块。warp 可先理解为按同一组指令协作的一小队 GPU 线程。

最主要的五个缺口是：

1. TMEM 不仅有容量，还要规定谁申请、何时交回分配许可、何时释放，以及两个 CTA 怎样协调。后来 `allocating_role` 只补负责人，没补所有释放时机。
2. 流水线不只“几层”，还要知道由线程还是异步 MMA 单元发出消费完成，以及顺序和集群屏障。
3. 能放几层流水线由共享内存扣掉其他开销后的余量决定，不能把层数和分配当互不相干数字。
4. 两个阶段共用物理存储会改变索引和遍历顺序；共用加载与存储区也会改变等待关系。
5. 静态循环取下个任务，和从硬件 CLC 队列领取任务，是不同机制，不能只写 persistent 就混为一谈。

其他具体压力包括缺少的 swizzle、每个操作数采用不同搬运方式、L2 遍历参数、每个角色不同寄存器预算和更多数据类型。列出需求还不是批准新字段，要先有明确类型、效果、检查和硬件证据。

跨 kernel 的 PDL 与带工作区修正的跨 CTA Split-K/Stream-K 分解归更高层。原文也发现 reduce_argmin 主要由本项目 Flash-KMeans 使用，提醒设计应看真实消费者，而不是追求词汇数量。
