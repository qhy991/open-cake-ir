# 把已有证据整理成逐项反馈

[English](../en/RUBRIC_FEEDBACK.md) · [中文入口](README.md) · [验收规则](ACCEPTANCE_GATES.md)

**Rubric 是给 Agent 看的证据检查表。它整理上一轮已经允许看到的反馈，帮助读者分清已知结果、缺失证据和待验证的修改方向。** 它没有加权总分，也不调用 LLM 裁判。

例如，一个候选没有通过后端支持检查，Agent 应先读具体拒绝原因。此时尚未得到 GPU 答案，不能写成“GPU 算错”。另一个候选虽然有稳定的探索计时，仍要经过共同 Evaluation 的确认，才能支持确认延迟结论。

## 在现有路径里怎样工作

Lab 从 StateCard 的 `previous_feedback` 生成 `rubric`，放进原有 provider 参考包。Agent 请求使用这个包，Evidence 保留同一份内容；原始反馈照常保留。检查表只整理当前反馈，不读取额外文件、另一实验臂的记录或受限参考实现。

实现入口是 [Lab](../../src/open_cake_ir/lab/) 中的 `rubrics.derive_rubric`；[任务包](../../src/open_cake_ir/lab/task_package.py)负责交付与保留。相同输入产生相同输出。它沿用 `matched_search` 和 Ralph 的任务路径，没有新的配置开关、运行模式或 provider 调用。

参考包中的 `rubric` 使用 `kind: evidence_rubric_v1`、`schema_version: 1`。`source` 指向 `/state_card/previous_feedback`；`criteria` 中每项包含 `criterion`、`state`、`evidence` 和 `guidance`。`evidence` 是指向该包原始反馈的 JSON 路径，便于核对来源。`guidance` 是固定的阅读或核实建议，不是已经完成的修改，也不保证修改会有效。

| 检查项 | 应读出什么 | 不能据此推出什么 |
| --- | --- | --- |
| `admission`，是否进入后续评测 | 当前记录是初始状态、拒绝，还是已有观察 | 未被拒绝就一定算对 |
| `correctness`，正确性 | 反馈是否报告通过或被正确性检查拒绝 | 静态检查通过等于 GPU 正确，或已完成框架 E2E |
| `measurement`，计时 | 是否测量，已有计时是否稳定 | 稳定就一定更快，或探索计时已得到确认 |
| `confirmation`，确认 | 是否已有确认结果 | 未确认的低延迟可以用于晋级 |
| `profile`，性能剖析 | 当前反馈是否报告剖析材料 | 文件存在就证明某个瓶颈或优化机制 |
| `findings`，诊断 | 原有诊断及其位置、阻塞与否 | 每条诊断都能阻塞，或报告之外没有问题 |

这是几项独立观察，没有“总体通过”或总分。没有观察、没有识别到支持的证据，或者反馈格式不符时，投影保留相应缺失、未知或格式异常状态，不补成成功。第一次调用尚无候选结果，也不会得到一次虚构的失败。

## 谁仍然决定对错与快慢

Workload Contract 仍拥有算子语义、输入和 oracle。Verifier 仍只在自己建模的域内阻塞；其通过结论不覆盖未分析的资源。共同 Evaluation 仍拥有外部参考正确性、配对计时和 fresh confirmation。候选选择、晋级、预算、停止条件和诊断路由保持原有权威，rubric 不参与这些决定。预算信息仍由原有 StateCard 提供，不另造“效率分”。

阅读时尤其区分三类情况：

- **后端覆盖不足。** 后端不支持某项寄存器或驻留控制，是当前表达或 lowering 的覆盖缺口。不能把它记成 GPU 正确性失败，也不能悄悄换架构。
- **性能材料存在。** Profile 记录存在，只说明反馈报告了材料。认定瓶颈需要读取实际指标并解释测量范围；认定修改的原因还需要受控比较。
- **已知证据与拟议修改。** “计时不稳定”是记录中的观察；“检查测量条件后再比较”是下一步建议。建议没有执行前，仍然没有新的测量或因果证据。

本改动属于 Lab 的反馈呈现。Compiler Revision、IR 词汇、Verifier 规则和已冻结历史 Evidence 不因此改变。Campaign 继续使用固定 Compiler；若未来确实需要缺失原语，须按独立的 Compiler 演进、Corpus Gate 和审查流程处理。Lab 可回放的运行源码变化也要遵守现有 Executor successor 流程，不能改写旧发布身份。

## 未来怎样检验反馈是否有用

**以下是未来实验设计，不是本次实现已经取得的结果。** 问题是：在证据完全相同的条件下，多一份逐项整理，是否让 Agent 更快找到正确且经确认的候选，并减少重复失败？

在一种固定的 Authoring Environment 内比较两个反馈条件：旧反馈原样交付；同样的旧反馈加上由它派生的 rubric。两组都能看到同一份原始证据，遵守相同参考访问限制。不要把“反馈呈现”与“Cake 或原生代码”两种处理混成一个对比。

预先在 Study 中固定任务、单一目标形状与输入分布、oracle 和容差、初始候选、精确 Compiler Revision、后端、工具链、GPU、Agent 模型与推理力度、scaffold、候选选择、计时边界、预算和停止规则。安排匹配的独立重复与运行顺序。新增反馈会占用 token，计入相同的预算，不额外补偿一次调用或一次评测。

两种反馈实现可以分别绑定加入 rubric 前后的 Executor Revision；需要核对实验差异只有反馈呈现，其余执行与评测规则一致，并分别满足资格要求。这不是新增运行开关的承诺。

| 要回答的问题 | 预先约定的观察 |
| --- | --- |
| 多久得到第一个正确候选 | 到首次 oracle 正确结果的轮数、已记录的时间、provider token 和评测次数；未达到者保留失败或缺失结果 |
| 是否少走同样的弯路 | 按预先定义的拒绝原因与诊断位置统计重复失败；环境故障单列，不算成候选算错 |
| 最终是否更快 | 相同预算下共同 fresh confirmation 的延迟；资格率与条件确认延迟分开报告，探索最小值不能替代它 |
| 收益花了多少成本 | provider token、总耗时、评测次数与测量开销；没有保留的时间或成本记为 unknown |

报告匹配重复的分布、失败、缺失与停止原因。不要只挑成功 Run，也不要为环境故障临时补跑。若要解释速度变化的机制，再另查匹配的 profiler 和受控修改证据。Study 拥有处理条件与分析，CampaignLock 拥有实际运行绑定；本页面不是新增合同或启动实验的命令。

本次源码和测试至多证明：投影遵守证据边界，Agent 请求与保留的参考包包含同一份反馈，原有决策流程仍适用。真实 provider 资格、GPU 结果、反馈对 Agent 的帮助、IR 的优势，以及目标框架 E2E，各自仍需要对应验证。参见[配对 CuTeDSL 流程](PAIRED_CUTE.md)和[先证明反馈有用的设计决定](adr/0010-feedback-before-agent-orchestration.md)。
